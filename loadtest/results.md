## Concurrency sweep (same box, single worker)

Throughput is bounded by a single GIL-bound Python process doing CPU-bound
XGBoost inference, so RPS plateaus around ~440 and latency grows once the
offered concurrency exceeds what one core can drain. Measured:

| Concurrency | Throughput | p99 |
|---|---|---|
| 1 | 244 RPS | 5.6 ms |
| 4 | 395 RPS | 13.1 ms |
| 8 | 446 RPS | 26.9 ms |
| 12 | 439 RPS | 55.5 ms |
| 64 | 228 RPS | 1722 ms |

Concurrency 8 is the sweet spot on this hardware. Past ~12 the request queue
in front of the single worker dominates latency without adding throughput
(concurrency 64 is included to show the saturation failure mode honestly).

## How this scales in production (not benchmarked here)

The numbers above are a **single uvicorn worker with the in-memory store**,
because this test machine has no Redis/Docker available. The intended
production configuration removes the single-process ceiling:

- **N workers behind the load balancer** (≈ one per core) scale throughput
  roughly linearly for this CPU-bound workload — ~10× on this 10-core box.
- Multiple workers require **shared state**, which is exactly what the Redis
  backend provides (the in-memory store is per-process). The Redis path is
  proven feature-for-feature identical to batch by `tests/test_streaming_parity.py`
  and comes up via `docker-compose.yml`, but its throughput was not measured
  here for lack of a local Redis server.
- A Redis round-trip adds ~0.2–1 ms per feature read on localhost — small next
  to the ~2–4 ms model inference, so per-request p99 stays well under 100 ms;
  aggregate RPS is then gated by worker count, not by the store.

Further headroom if ever needed: batch inference across in-flight requests,
C-serialize the feature row, and keep SHAP (`explain=true`) off the hot path
(it already defaults off).
